# Subscriptions ("Plus") on Google Play and the App Store
Checked 2026-11-25. Items marked (unverified) came from a secondary source or memory; re-check before building.

## Recommendation: RevenueCat behind `src/platform/` (purchases adapter) and `functions/src/adapters/`
Why: one SDK and one entitlement model for both stores; store receipt validation, renewals, grace periods and refunds are handled for us; a webhook plus a server REST call gives the backend a trusted answer; free until revenue is meaningful. Plain native plugins would mean writing and running our own Play Developer API and App Store Server API receipt checks, notifications and edge cases (the work RevenueCat sells). The adapter keeps a later swap possible.

## Facts
- Price: <https://www.revenuecat.com/pricing> (read 2026-11-25): no charge up to $2,500 monthly tracked revenue (MTR), then 1% of tracked revenue; all features included. MTR is counted before the store's cut. Older pages still show $1,000/$10,000 thresholds; ignore those.
- Capacitor: official plugin `@revenuecat/purchases-capacitor` (<https://www.revenuecat.com/docs/getting-started/installation/capacitor>, read 2026-11-25). Version seen: 13.0.1 (npm mirror, socket.dev; check npm). Do not add the iOS SDK separately; it is bundled. Optional `@revenuecat/purchases-capacitor-ui` (paywalls, customer center; keep the same version as the main plugin; iOS needs SwiftUI capability). We would build our own paywall for the Plus-vs-free table, so the UI package is optional. iOS needs the In-App Purchase capability (shared file: Xcode project, integrator).
- Server side (<https://www.revenuecat.com/docs/integrations/webhooks>, read 2026-11-25): HTTPS endpoint, choose production/sandbox/both, authorization header checked on each POST, optional HMAC signature (`X-RevenueCat-Webhook-Signature`, verify on raw body, about 5 minute tolerance). Reply 200 fast; up to 5 retries over about 80 minutes; deliveries can repeat so be idempotent on event `id`. Docs advise calling `GET /subscribers` after any webhook rather than trusting the payload alone.
- Sandbox: RevenueCat detects the store sandbox on its own and tags events `SANDBOX`; sandbox and production data can be toggled apart (<https://www.revenuecat.com/docs/test-and-launch/sandbox>, read 2026-11-25). Store-side setup (Apple sandbox Apple IDs / TestFlight, Play license testers and an uploaded internal-testing build) was not on that page; follow each store's own page (unverified here).

## Fit with this app (Plus is per kitchen)
Set RevenueCat app user ID to the Firebase uid of the kitchen creator (only the creator manages Plus, spec open question 10). Webhook function (Cloud Function, own adapter) verifies the header, calls `GET /subscribers`, and writes `plus: true/expiry` on the kitchen document. Clients read the kitchen document; usage limits are enforced in the backend, never trusted from the app. Apple Family Sharing for subscriptions would not map to our kitchen model: grant Plus through the kitchen, not through Apple's sharing.

## Store commission (small developer)
- Google Play, US, from 2026-06-30 (<https://support.google.com/googleplay/android-developer/answer/112622>, read 2026-11-25): auto-renewing subscriptions on the first $1M of annual earnings are 10% plus a 5% billing fee when bought through Play Billing, so about 15% in total. The "standard" row for subscriptions shows the same 10% + 5%. Enrolling in the reduced-fee program through an account group may still be needed; confirm in Play Console (owner step).
- Apple (<https://developer.apple.com/app-store/small-business-program/>, read 2026-11-25): Small Business Program is 15% on paid apps and in-app purchases if proceeds were no more than $1M in the previous calendar year; above $1M the standard rate applies for the rest of the year. It must be applied for in App Store Connect (owner step; unverified here that it is an application, not automatic). Standard rate 30% (unverified here; and 15% after year one of a subscription is the standard-rate rule, unverified).
- RevenueCat's 1% comes on top, only above $2,500 MTR.

## What the paywall must show
- Apple, Review Guideline 3.1.2 (<https://developer.apple.com/app-store/review/guidelines/>, read 2026-11-25): subscription must give ongoing value, last at least 7 days, work on all the user's devices; describe clearly what the user gets for the price; do not make users post, upload contacts, etc. to get what they paid for; communicate the items in Schedule 2 of the Apple Developer Program License Agreement (not read). From memory (unverified): subscription name, length, price per period, auto-renew and how to cancel, working links to privacy policy and Terms of Use.
- Apple 3.1.1: unlocking features must use in-app purchase, no license keys or other own mechanisms.
- Google Play (<https://support.google.com/googleplay/android-developer/answer/9900533>, read 2026-11-25): clearly and accurately state offer terms, cost, billing frequency, auto-renewal, whether a subscription is required to use the app; offer must be dismissable if not required (ours is not required, so show a visible close); show the amount actually charged, not just a monthly breakdown; trial and intro offers must state duration, price after, when they convert and how to cancel; do not disguise one-time benefits as subscriptions.
- Our paywall therefore: price per period in the user's currency from the store (not hard-coded; the price is a server setting but the store product defines the charge), renewal and cancel text, links to Terms and Privacy, a Restore purchases button, and a clear Not now. Plus is recurring value (allowances every month), which fits both stores.

## Owner-only steps
Create Play and App Store developer accounts; create the subscription product in both consoles; bank and tax forms; RevenueCat account and API keys (into `secrets/`); Small Business Program enrolment; sandbox testers.
