# Order email intake: forwarding address and Gmail connect
Read 2026-11-25. Prices change; re-check before the owner commits. "Not stated" means the official page did not say.

## A. Inbound email services (forwarding address, one private address per kitchen)
Design: owner buys or has a domain, points MX at the service (or uses the service's own subdomain), each kitchen gets `<random-token>@in.<domain>`; the service POSTs to an HTTPS Cloud Function, which checks the token maps to a kitchen, checks sender and SPF/DKIM, keeps only items, and drops the rest. A token in the address is a secret; rotate on demand.

## B. Gmail connect
Scopes (https://developers.google.com/workspace/gmail/api/auth/scopes): `gmail.readonly`, `gmail.metadata`, `gmail.modify`, `gmail.compose`, `gmail.insert`, `mail.google.com` and settings scopes are all Restricted. `gmail.metadata` (headers only, no body) is narrower but still restricted, and the list method says the `q` filter cannot be used with it (https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list). So it cannot filter by sender and cannot read the item list. Add-on scopes (`gmail.addons.current.message.readonly`) are Sensitive, but only work inside a Workspace add-on that the user is running; not a fit for a phone app.
Conclusion: there is no narrower scope that reads only one sender's messages. Read with `gmail.readonly` and `q=from:...` (the API supports Gmail search syntax; https://developers.google.com/workspace/gmail/api/guides/filtering). The sender restriction is our code, not a Google permission. Do not claim "we only read Instacart" to Google as technical enforcement; say it is a policy and filter.

Verification (https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification), all OWNER: check exceptions; verify the domain in Search Console; public home page and privacy policy on that domain; Verify and Publish branding; declare scopes in the Verification Center; unlisted YouTube demo video showing the consent flow and each scope's use; explain why narrower scopes are not enough; answer Trust & Safety follow-ups.
Security assessment (https://support.google.com/cloud/answer/13465431): annual, final step, Google contacts the owner when due; uses CASA (App Defense Alliance), risk tiers AL1/AL2; passing gives a Letter of Validation; revalidation every 12 months. Done by an independent assessor authorized by the Alliance (labs include TAC Security, Bishop Fox, NCC Group, others: https://appdefensealliance.dev/casa/casa-assessors). When: required if the app accesses restricted data "from or through" a server, or stores or transmits it on servers (verification page). Official Google pages state no price. Third-party reports: TAC Security's own FAQ lists Tier 2 Basic at $540 per app, with Premium around $720 and higher plans up to about $1,800 (https://tacsecurity.com/?p=16935, via search snippet; unverified here); older press cites $15,000 to $75,000 for audits (2019, probably Tier 3). Treat as roughly $540 to a few thousand per year for Tier 2, but get a quote.
What counts as server storage or transmission: not defined on the pages read. Plain reading: our Cloud Function fetching mail with the user's token, or any token or message body passing through our backend, counts. An on-device design (the phone app calls Gmail directly, parses on the phone, sends only the item list to our backend) might avoid the CASA requirement but still needs the restricted-scope verification; this is a reading of the wording, not an official ruling. Ask Google before relying on it. A phone cannot receive new mail in the background without polling or a server watch, which would break this.
Unverified-app limits (https://support.google.com/cloud/answer/15549945): Testing mode = up to 100 test users listed by the owner; their consent and refresh tokens expire after 7 days (so reconnect weekly). An unverified app shows a warning screen and can add only 100 new users over the project's lifetime, never reset; the cap does not apply once approved. Verification is not needed while status is Testing.

## Only the owner can
Pick and pay the inbound email service, own the domain and DNS; create the Google Cloud project, consent screen, domain verification, demo video, verification submission; pick and pay the CASA assessor each year; add test users.

## Effects on the plan
- Gmail connect cannot be sender-limited by scope; the privacy policy and consent text must say so honestly.
- Until approval, Gmail connect runs only for up to 100 owner-listed test users with weekly re-consent; forwarding must carry launch (already the decision).
- Gmail connect through our backend triggers the annual CASA assessment; consider asking Google about the on-device variant before building the Cloud Function path.
